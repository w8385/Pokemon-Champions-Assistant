# 8메뉴 UI 갱신: 유한 단계 구현 계획

**계획일 뿐 구현·테스트·배포 완료 아님.** [requirements.md](requirements.md)의 소유권/보존 계약과 [acceptance-ledger.md](acceptance-ledger.md)의 8개 행을 종료 기준으로 사용한다. 근거는 `/home/w8385/.hermes/artifacts/pokemon-champions/whole-app-ui-refresh/`의 소스 요구사항·컴포넌트 실사·공개 앱 읽기 전용 감사. 공개 앱 리비전과 소스 기준 `f61858f`의 일치를 검증하지 않았으므로 첫 구현 전에 현 브랜치/마운트 상태를 다시 고정한다.

## 1. 상대 종 검색을 기존 실제 공용 입력으로 (P0)

- `App.tsx`의 상대 빠른 입력 두 위치와 상세 종 입력의 독립 `<input>`/목록/강조/Enter 상태를 조사하고 `PokemonSearchField`→`SearchCombobox`의 **입력 소유**로 순차 치환. 기존 `commitOpponentQuickSearch`/`selectSpecies`만 선택 시 호출하며 draft는 각 호출자가 유지. 필요한 경우 공용 입력에 최소 `inputRef`/명시 focus API를 추가해 다음 빈 슬롯의 **보이는** 입력에 초점을 준다. 동시 마운트 ID 충돌과 채워진 전체 슬롯의 덮어쓰기 정책은 먼저 확인하고 암묵 변경하지 않는다.
- 완료 게이트: 첫 후보/화살표/Enter/클릭 동일 순위, IME·229/Escape/Tab/blur 비등록, 실제 선택 시 슬롯·다음 빈 슬롯·초점, 모두 찬 상태/기존 다른 슬롯 보호. 파티·빌더·계산기·스피드라인·도감 필터의 기존 공용 검색 회귀. 독립 상대 기록 초기화의 확인·부분 실패는 별도 보호 fixture로 고정.

## 2. 공유 대면/계산 작업면의 입력↔결과 근접성 (P1)

- 이미 공유하는 `QuickDamagePanel` 안에서 두 카드, 같은 척도의 유효 스피드, 기술칸별 피해 프리뷰, 선택 피해/조건의 **DOM 순서와 간격**을 조정. 빈 계산기에서 결과가 두 종 입력 앞에 오는 문제와 대면에서 결과가 카드보다 앞·조건이 뒤인 문제를 해소한다. 390폭 카드 내 4기술은 우선 읽히는 한 열, desktop은 2×2를 실제 측정 후 확정; 카드 좌우 배치는 가독성과 overflow를 함께 비교한다. 실수치/조건·16난수·미지원 이유·기존 모달을 유지한다.
- 완료 게이트: 슬롯/카드 종 동일성, 1기술만 있는 피해, 양방향 4기술·공수 교체, 속도 동속/차이와 트랙 물리 폭, 조건 변경의 즉시 결과, 종·슬롯 교체 시 양측 임시 가정/모달 정리, 단측 원본 반영 시 반대 초안 보존. 대면 슬롯·seed 저장과 계산기 독립 저장 각각 reload/readback, 저장 실패 경고, 1280/390 동일 상태 첫 입력·첫 결과 좌표 및 기술/모달 클릭 검사. 엔진/저장 스키마 변경 없음.

## 3. 빌더와 공용 카드 머리·기록 행동 근접성 (P2)

- 빌더 이미지/검색/타입 머리에 기존 `PokemonCardHeading`을 **실제** 재사용할 수 있는지 콜백·팝업·CSS 층위를 먼저 조사한다. `PokemonStatGrid`, `PokemonBuildFields`, `RegisteredMoveSlot`, `EffortTuningModal`을 유지하고 새 유사 편집기를 만들지 않는다. 빌더의 속도 1스탯/화력 2스탯 **인라인 노력 즉시 조정**은 현재 사용 중이므로 삭제하지 않고 전체 6스탯 모달과 각각의 역할을 보존한다. 카드 편집→스피드/피해 결과→저장/초안 불러오기/파티 적용의 거리와 대상 라벨을 최소 변경한다. 파티의 카드→분석 DOM 순서는 이미 맞으므로 뒤집지 않고 첫 종 입력과 프리셋/OCR 위계를 측정한다.
- 완료 게이트: 빌더 초안/개인 저장본/파티 슬롯 적용의 대상과 확인·취소·reload readback, 4기술/effort 제한·마법 수치/모달 focus, 파티 6슬롯 뒤 분석·18×6 표, 같은 종 다중 슬롯 범위, 라이브러리 읽기 전용 가져오기와 도감 명시적 빌더/파티 이동. 동일 행동의 단순 외형 일치가 아닌 실제 callback·IME·tooltip 검증.

## 4. 8메뉴 마운트 QA → 회귀 → 독립 검토 → 배포 검증 (P3)

- 헤더/홈의 8개 링크, 숨은 더블·구 경로, 각 메뉴의 첫 행동/결과/저장 또는 읽기 전용 상태를 원장 8행 모두에 **실행 판정**한다. 데스크톱/390폭에서 실제 좌표·순서/폭·가독성과 KO/EN/JA를 기록한다. SpeedLine URL 3×2 조건·복구/44px 대상, 라이브러리 상세 href/출처, 도감 전체 ID/상세·Back/reload/로딩 실패, 파티 분석 순서를 빠뜨리지 않는다. 모바일 viewport 포인터와 실제 터치를 다른 칸에 기록한다.
- 각 작은 수직 조각마다 실패하는 회귀 테스트를 먼저 추가한 뒤 해당 조각 통과, 전체 테스트·`npm run typecheck`·`npm run build`·`git diff --check`를 실행한다. 브라우저 QA는 원래 저장 상태를 백업하고 종료 시 동일 오리진 비마운트 문서에서 복구·정확한 readback 후 떠난다. 최종 마운트 QA 뒤 소스를 동결하여 독립 검토하고, 수정이 생기면 영향받은 QA/검토를 다시 한다. 검토 통과 후 실제 배포 리비전을 읽어 동일 숫자 fixture·직접 링크·reload를 공개 앱에서 재확인한다. 어떤 게이트가 막히면 `FAIL`/`PARTIAL`/`NOT TESTED`로 남기고 완료라 하지 않는다.

## 작업 경계

`App.tsx`/통합 테스트는 한 작성자, 공용 컴포넌트/테스트는 한 작성자, `styles.css`/작업면 CSS는 한 작성자가 직렬 통합한다. 레거시 경로·8개 평면 내비게이션·숨은 더블·계산 엔진·기존 데이터 소스·스키마/저장 키·기록/초안 구분을 보존한다. 읽기 전용 근거를 테스트 통과나 출시 승인으로 바꾸지 않는다.
